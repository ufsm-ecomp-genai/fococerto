## 1. Zetaris: the data layer

### Sources federated by Zetaris
| Source | Content | How it enters Zetaris |
|---|---|---|
| NASA FIRMS (VIIRS S-NPP, 7-day CSV) | detections: lat, lon, time, confidence, FRP, day/night | `scripts/ingest_firms.py` → **Postgres** table `focos` → Zetaris JDBC datasource `fococerto_pg` (`CREATE DATASOURCE` + `REGISTER DATASOURCE TABLES`) |
| GeoNames `cities1000` | localities and population | CSV in the **Zetaris file store**: `docker cp` + `CREATE LIGHTNING FILESTORE TABLE localidades … FORMAT CSV` |
| OpenStreetMap (Overpass) | fire stations | file store CSV `bases` |
| Official regional station list (`config/regioes/<region>_bases_oficiais.csv`) | stations with agency, source URL and year (Tocantins: 12 stations from CBMTO, Prevfogo/Ibama Portaria nº 114/2024 and ICMBio) | file store CSV `bases_oficiais` (extra `regiao` column), read by `RepositorioZetaris.bases()`; if that table is missing it falls back to the local CSV and records why (`erro_bases_oficiais`) |
| Region table | bbox, exposure radius, weather grid step | file store CSV `regioes` |
| Open-Meteo | VPD, wind, humidity, precipitation on a fixed 0.5° grid | `CREATE LIGHTNING REST TABLE clima_<region>_raw` + **`CACHE TABLE`** (REST tables are re-fetched on every query; the cache is lost when Zetaris restarts, so `setup_zetaris.py --so-cache` and `RepositorioZetaris.aquecer_cache()` redo it) |

Everything is registered **by script**, never by hand: `scripts/setup_zetaris.py` (`--dry-run` prints every command without a Zetaris).

### Views (`sql/zetaris_views.sql`, `CREATE SCHEMASTORE VIEW … WITH CONTAINER fococerto`)
1. **`ocorrencias`**: detections grouped into ~0.1° cells per UTC day: count, FRP sum and max, first/last time, consecutive days with fire ("islands" of consecutive days via window functions), detections the day before.
2. **`ocorrencias_localidades`**: localities within the exposure radius of each cell, with distance.
3. **`ocorrencias_contexto`**: nearest weather grid point, population within the radius.
4. **`ocorrencias_prioridade`**: the transparent priority formula (exposure, intensity, weather, persistence, growth) with each component exposed as `c_exposicao` … `c_crescimento`.

Plus two weather views generated by the script: `clima_<region>` (flattens the Open-Meteo JSON with `posexplode`) and `clima` (union of all regions). The views use only subqueries (no CTEs) to be safe with the Zetaris view parser.

### How the app uses it
`app/data/repositorio.py::RepositorioZetaris` sends one SQL statement per request to the Zetaris REST endpoint (`/sql-editor/sqls/run`) and reads `fococerto.ocorrencias_prioridade` and `fococerto.ocorrencias_localidades`; the Analyst's `historico_celula` reads `fococerto_pg.focos` through Zetaris; `bases()` reads `fococerto_arq.bases_oficiais` and `fococerto_arq.bases` and merges the station layers (official, OSM, estimated) with `app/data/bases.py`, so each station in the plan carries its source and layer. If the views fail, it falls back to computing occurrences in Python **from data still read through Zetaris** (`fococerto_pg.focos`, `fococerto_arq.localidades`, `fococerto.clima`) and records which path was used (`modo_usado`). Writes (approved decisions, coordinator notes) go straight to Postgres, because Zetaris is read-only over its sources.

## 2. Meterless Engine: H-MEM

### What we implemented
`services/hmem/` is an HTTP service (TypeScript, Node 24, port 7070) around the **official Meterless H-MEM reference engine** (`github.com/meterless/meterless`, `engines/hmem/reference`, commit `1742dec`, Apache-2.0), copied into `src/engine/`. The conformance runner and vectors are copied **unmodified**. Our changes to the engine are few and each is marked `FocoCerto adaptation` in the source and listed in `services/hmem/NOTICE`:
- accent folding before tokenizing (identity on ASCII);
- Portuguese correction language for automatic supersedes ("na verdade", "em vez de", "deixou de"…);
- Portuguese opposing pairs for conflict detection (`alagada/bloqueada/interditada/fechada` × `liberada/aberta/desbloqueada`, …), plus `scanFor()` and `resolveBySupervisor()` (additive).

The service adds: one `HMEM` instance per region (`data/<region>/state.json` + `ledger.jsonl`), explicit `supersedes` (it sets `supersededBy` on the old record so the reference ranking penalty applies), and a coordinator policy (`HMEM_POLITICA_NOTAS=coordenador_mais_recente`, default): when the engine queues a conflict between a new and an older coordinator note, the newest note wins via the engine's supervisor resolution, recorded in the ledger. Nothing is ever deleted.

`app/memory_client.py` has `ClienteHMEM` (HTTP client of the service) and **`MemoriaLocal`**, a Python port of the engine and service layer, persistent in JSON, used in sample mode. `tests/test_memoria.py::test_local_e_servico_concordam` checks that both give the same results.

### What it does in the product
1. **Coordinator notes change the plan.** `python -m app.cli nota --regiao tocantins "estrada para São Félix alagada"` stores a memory (São Félix do Tocantins hosts a Prevfogo/Ibama brigade station from the official layer). In the next run the graph recalls it, `interpretar_memorias` turns it into a candidate fact (route/base blocked), `checar_regras` flags `restricao_memoria`, and the **Critic decides** whether the exception applies (source, confidence) and writes the counter-proposal. Reproduced in sample mode on the 23 Oct data: `saofelix-t1` stops going by road to `cel_-96_-468` (Lizarda), stays in reserve, and that occurrence is escalated (6 → 5 assignments, 9 → 10 escalations; `output_examples/tocantins-escasso-com-nota/`).
2. **Supersedes.** A later note "estrada para São Félix liberada" is detected by the engine as conflicting (opposing pair on similar content) and wins: the CLI prints `Substitui a memória tocantins:mem-1.`, the old note drops out of the active recall, and the plan sends `saofelix-t1` back to Lizarda (6 assignments, 9 escalations). The plan's "memories" section shows `tocantins:mem-2 … substitui tocantins:mem-1`.
3. **Per-region memory.** Memories of different regions never mix (ids `<region>:mem-<n>`; `supersedes` must point to the same region). Tested in `test_escopo_por_regiao`.
4. **Data-derived memories** (type `derivada`, e.g. "cell X was deprioritized and grew 3×") raise the priority of that cell. They are **learned automatically between periods** (`app/agents/aprendizado.py`, called by `run`): cells left without a resource that grew or stayed strong in the next FIRMS data become memories, and a cell cited by such a memory is pulled into the period list even if it is outside the top 15. Shown end to end by `scripts/demo_3_periodos.sh`; in the single-period ablation these memories are seeded by the scenario.

### The test that shows it works
```

  ...
  conflict-gate

  ledger-audit
```

The suite runs against `src/engine/index.ts`, the same engine the server uses; the output is committed in `services/hmem/conformance-report.txt`. Our own tests add a **3-period test** (`tests/test_memoria.py::test_tres_periodos`: note → derived memory → contradicting note that supersedes → recall shows active and superseded → nothing deleted), explicit supersedes validation, region scoping, persistence across service restarts, and the CLI integration tests `test_nota_persiste_em_disco` and `test_nota_aparece_no_run_seguinte`.

## 3. Meterless Nightshift: the AI provider

### How the app connects
All LLM calls go through `app/llm/client.py::chat()` (a test forbids direct provider calls anywhere else). With `LLM_PROVIDER=nightshift`:
- `POST {METERLESS_BASE_URL}/chat/completions` (OpenAI-compatible), `Authorization: Bearer $METERLESS_RUNTIME_TOKEN`, headers `meterless-app: fococerto` and `meterless-scope: user`, model `METERLESS_MODEL`. We ask for Nemotron by name (`nvidia/nemotron-3-ultra-550b-a55b`, as in `.env.example`): with `meterless/auto` the router may try to load a local model instead. The token is the content of the runtime's `proxy-token` file; the token shown in the Nightshift UI returned 401.
- Retries with exponential backoff on 408/409/425/429/5xx and transport errors; client errors are not retried.
- JSON outputs are requested with the schema in a system message, then validated with pydantic by the agent; on invalid output or an unreachable Nightshift the agent falls back to its deterministic logic and logs `status: fallback_offline`.
- **Reasoning is off by default** (`LLM_NO_THINK=1`): the request carries `chat_template_kwargs: {"enable_thinking": false}`, plus a `/no_think` system message. Measured on the real Nightshift: with reasoning on, Nemotron spent the whole 4096-token budget thinking and never wrote the JSON (the Planner's prompt is large), and `/no_think` alone was not enough; `enable_thinking=false` fixed it. `LLM_NO_THINK=0` turns reasoning back on. The client also strips any reasoning text that comes glued before the answer (everything up to the last `</think>`).

### What is logged
Every call (success or failure) becomes an `llm_call` line in `logs/<run>.jsonl` with **`modelo`** (the `model` returned), **`routed_model`** (the model Nightshift actually routed to) and **`receipt`**, plus tokens, latency and number of attempts. On the real Nightshift each response carries a signed receipt (`meterless.compute_receipt.v1`, Ed25519) with `routed_model` and a `receipt_id` (e.g. `rcpt_req_7yxkcil7`); the app logs the routed model and the receipt id. `_extrair_meta` looks for them tolerantly in the body (`meterless_receipt`, `receipt`, `meterless`) and in response headers. `tests/test_llm_client.py` checks this with a fake response (`routed_model: "nvidia/nemotron-x"`, `receipt: "rcpt_123"`).

### Test status (honest)
**Working against the real service since 25 Oct 2026 (~01:00 UTC).** Nightshift for Windows runs on a team machine with an NVIDIA GPU and the app reaches it over Tailscale. The first LLM-mode period on the scarce scenario took about 23 s with 2 calls (Planner and Critic), each logged with `routed_model` and its receipt id; with the current review loop a real period took 1.5–3 min with 4 calls (Planner, Critic, Planner, Critic) in our runs. The **LLM-mode ablation is complete**: 144 runs, 450 Nemotron calls (449 valid on the first try, 1 recovered by retry, 0 offline fallbacks), mean latency 29 s; results in the README and `eval/RELATORIO.md`. To switch it on: run Nightshift, put the NVIDIA key in Nightshift's Providers tab, set `LLM_PROVIDER=nightshift`, `METERLESS_BASE_URL`, `METERLESS_RUNTIME_TOKEN` (the `proxy-token` file) and `METERLESS_MODEL` in `.env`, and run without `--sample`.

## 4. NVIDIA: Nemotron through Nightshift

The Planner, Critic and Analyst run on **NVIDIA Nemotron** (`nvidia/nemotron-3-ultra-550b-a55b`) routed by Nightshift; NVIDIA is never called directly from the project. Nemotron makes the decisions the code deliberately does not: deviating from the greedy baseline with a justification, judging trade-offs and memory exceptions, deciding when to escalate, and concluding (with confidence) whether an occurrence looks like agricultural burning. The model that answered each request is recorded in the log (`routed_model`).

**Status:** real calls work (section 3); the model that answered is in `routed_model` of every `llm_call`. In the first LLM-mode ablation the full system (C) passes 75.9% of the answer-key checks against 22.2% for the simple allocator and 65.4% for the Planner with the rule checker alone (B), and no final plan carries a false citation. Two honest caveats from that run: the memory gain over C without H-MEM is within run-to-run noise, and every LLM-mode escalation came from a deadlock after 3 rounds. The second LLM run, after the fixes (48 runs, 137 calls, 25 Oct evening), gives A 22.2%, B 77.8%, C 82.8%, D 82.8%: impasses went from 30 to 6, and the system rewrote **24 wrong facts** written by Nemotron (12 distances, 6 localities, 6 populations) before the Critic saw the plan. (An earlier figure of "about 50 wrong facts" from the first run overstated the model's errors: part of those flags were false positives of our own checker, since fixed.) Details in the README and `eval/RELATORIO.md`.

**Plan language.** Nemotron writes the plan text (justifications, the Critic's reasons, the Analyst's opinion, the summary) in the language of the run: `run --idioma en` (or `idioma` in `POST /api/run`, or `FOCOCERTO_IDIOMA`). The prompts get an "output language" block and the data an `idioma_saida` field; ids and place names stay as in the data. The citation checker reads English facts too ("87,545 people", "arrives in 2.4 h", "within the 6 h limit"). Real English runs on 25 and 26 Oct produced English plans; in the first one the checker caught and rewrote one wrong locality.

### What the system does when the model is wrong (a real case)
In a real English run (26 Oct 2026, 18:08 UTC, run `20261026T180817-eca168`; scarce scenario, cached real data, Nemotron 3 Ultra through Nightshift, 4 calls with receipts `rcpt_req_h6x03q83`, `rcpt_req_kge1hs2l`, `rcpt_req_kzxa7ccp`, `rcpt_req_nuo48sqb`), the Planner's round-2 summary said:

> "Nine incidents remain without viable resource and must be escalated: cel_-91_-474 (2135 people), **cel_-117_-491 (87545 people, covered by gurupi-t1)**, …"

`gurupi-t1` does not exist in that scenario, and the plan had no resource on `cel_-117_-491`, the occurrence with the largest exposed population. The model had invented a resource and a coverage. What happened next, from the log:
1. `checar_citacoes` flagged `gurupi-t1` as `id_inexistente` (once in a justification, once in the summary), and `checar_resumo` flagged `gurupi-t1→cel_-117_-491` as `cobertura_falsa` (real resources on that cell: none). It also caught a wrong locality ("Gurupi" where the data say Porto Nacional).
2. Before the Critic saw the plan, the system rewrote the summary from the final assignments and logged one `ferramenta`/`citacao_corrigida` event with the 4 corrections. The new summary: *"6 assignment(s): palmas-a1→cel_-103_-478, … Without a crew: cel_-91_-474, cel_-117_-491, … (Summary rewritten by the system from the final assignments: the agent's summary cited a nonexistent id or a coverage that does not match the plan.)"*
3. The Critic (Nemotron) approved the corrected plan, and the graph's guard rail escalated every exposed occurrence left without a resource. The published plan says: *"ESCALATED cel_-117_-491: Mandatory: 87545 people exposed and no crew/aircraft assigned in the final plan. Suggested action: request external support."*

The real run (plan, map and trace) is in `output_examples/nemotron-invented-id-en/`; `tests/test_citacoes_ids.py` reproduces the case with the same ids and the same summary sentence, in English and Portuguese. **Limits:** the coverage check is a heuristic over two sentence forms ("X covered by R", "R → X"), so a claim phrased differently is not caught; escalation reasons are not checked. The point is not that Nemotron is unreliable: it is that an invented id or a false coverage claim in the forms we check does not reach the coordinator, whatever the model writes, and the correction is in the log.

## 5. What was unique about our use

- **Zetaris does the analytics, not just the plumbing.** The occurrence clustering, consecutive-day persistence, exposure and the whole priority formula are SQL views federating three kinds of sources (Postgres, file-store CSV, REST with cache). On the real Zetaris the priority view returns the same 698 occurrences as the Python implementation, so the sample mode and the Zetaris path give the same numbers.
- **Every station shows where it came from, and the official layer is meant to be federated.** Stations come in layers (declared by the coordinator, official list with a source per row, OpenStreetMap, estimated municipal seat), merged under 3 km, and each plan shows the layer and the source. In a real deployment the official layer would be the agency's own system (e.g. Sisfogo) federated through Zetaris instead of a CSV, which is exactly what a federation layer is for; how many crews each station has stays an input from the coordinator.
- **H-MEM is the reason a plan changes between periods.** A coordinator's field knowledge ("this road is flooded") becomes a memory that the Critic weighs against the rules, and a later correction supersedes it with a full audit trail, without deleting anything. Memory is scoped per region, so the same deployment can serve several regions.
- **We used the official reference engine and its conformance suite as-is**, with small, marked, additive adaptations for Portuguese, instead of re-implementing H-MEM, and kept a Python port verified against it for offline use.
- **The model's text is checked against the plan.** Every fact and id Nemotron cites is re-checked against the run's data, and a summary that claims a coverage the assignments do not have is replaced before the Critic and before publishing, with the correction logged (section 4).
- **Every model decision is auditable.** The log ties each decision to the tool evidence, the memory used, and the model that answered (`routed_model`, `receipt`), and the ablation (A/B/C/D) measures whether the LLM Critic and the memory actually improve decisions, with answer keys committed before any run.
